일반 락(`synchronized` 블록, 뮤텍스)은 한 프로세스 안의 스레드를 조율한다. 서비스 인스턴스를 둘 띄우는 순간 그 락은 인스턴스 사이에선 무용지물 — JVM마다 자기 락이 따로다. **분산 락**은 락을 모든 인스턴스가 공유하는 곳(DB 행, Redis, ZooKeeper)으로 옮긴다.

## 왜 중요한가

스케줄 잡을 수평 확장하면 모든 인스턴스가 동시에 같은 잡을 쏜다. 공유 락이 없으면 중복 실행 — 같은 배치가 두 번, 행이 이중 적재.

## 어디서 썼나

목적은 같고 층위가 다른 세 가지:

- **잡 레벨**: `job_lock` 테이블 위 ShedLock으로 원가원장 마감을 한 인스턴스만 실행하고, `@Async`로 독립적인 공장 마감들은 서로 안 밟으며 병렬 실행.
- **행 레벨**: Oracle `SELECT ... FOR UPDATE`로 멀티 인스턴스 MES의 ID 생성을 직렬화 — 중복 ID가 나오던 게 다음 시퀀스 값의 read-modify-write [[경쟁 상태|race-condition]]였다.
- **어드바이저리**: DocVault에서 해시 체인별 `pg_advisory_xact_lock` — 동시 INSERT가 같은 `prev_hash`를 읽어 감사 체인을 분기시키고 있었다.

## 함정

락 자체가 정확성은 아니다. 보유자가 락 만료를 넘겨 멈추면(GC, 네트워크) 두 번째 보유자가 락을 얻는데 첫 번째는 여전히 자기 거라 믿는다 — **펜싱 토큰**이나 커밋/롤백 시 풀리는 트랜잭션 범위 락이 필요하다. 그리고 분산 락은 처리량 상한이다: 락이 지키는 모든 게 직렬화된다. 종종 **유니크 제약**이나 [[멱등|idempotent]] 설계가 락보다 싸다.

## 번역 노트

"분산 락" — 보통 "잠금"이 아니라 "락"으로 음차한다. 실무에선 "락 잡는다"고 말하고, "잠금"은 화면 잠금 같은 UI 락으로 읽혀서 동시성 맥락엔 외래어가 살아남았다.
